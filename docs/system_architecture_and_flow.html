🏗️ High-Level System Architecture

The Blood Aid platform is structured as a TypeScript monorepo using pnpm workspaces. It cleanly decouples the user-facing web application, the backend domain micro-services/modules, and shared contract models.

Frontend Layer (`apps/web`)

• Next.js 15 App Router & React 19
• Server Components for SEO & fast initial loads
• Client Components for real-time interactivity
• Next.js API Proxy (`/api/proxy/[...path]`) injects HttpOnly JWT cookies securely
• TanStack Query for client-side caching & mutations

API Gateway & Backend (`apps/api`)

• NestJS 10 with modular dependency injection
• TypeORM with PostgreSQL
• PostGIS spatial queries (ST_DistanceSphere, ST_MakePoint)
• Redis with Cache Stampede protection (Single-flight mutex & jittered TTL)
• WebPush integration for instant donor emergency alerts

Shared Contracts (`packages/shared`)

• Zod validation schemas for forms and payloads
• Strict Enums: BloodGroup, RequestStatus, UrgencyLevel, ComponentType, UserRole
• Blood compatibility matrix calculation rules
• Formatted labels and sanitizers shared by both web and api

🔄 Full-Stack Data & Security Flow

1

Browser Interaction

User clicks an action on the Next.js UI (e.g., submitting a blood request or accepting a donor offer).

TanStack Query mutate() -> apiClient.request()
2

Next.js Reverse Proxy & Cookie Guard

Next.js route handler reads secure access_token from HttpOnly cookie and attaches Authorization: Bearer <token> to the upstream request.

apps/web/src/app/api/proxy/[...path]/route.ts
3

NestJS Guards, Pipes & Filters

JWT Auth Guard validates user token. Roles Guard enforces ADMIN permissions where required. ValidationPipe parses and whitelists payload via class-validator & Zod.

JwtAuthGuard -> RolesGuard -> ValidationPipe
4

Service Layer, Redis Cache & Database

The Service layer performs business validation (e.g. eligibility cooldowns, spatial radius computation), updates PostgreSQL with TypeORM, and invalidates or updates Redis caches with stampede protection.

Service.method() -> CacheManager -> TypeORM Repository -> PostgreSQL

👥 What Can Be Done — Perspective by Role

Whether you are a donor, patient in urgent need, or platform moderator, here is what the platform enables:

🩸

As a Blood Donor

  • Set Availability & Profile: Register blood group, location coordinates, health notes, and last donation date.
  • Smart Feed: Browse urgent requests matched to your exact blood compatibility (e.g., O- see all, A+ see A+ and AB+).
  • Emergency Distance Alerts: View how many kilometers away a hospital or patient is.
  • Offer Help: Submit a response expressing readiness to donate for an open request.
  • Safety Cooldown: Automatically protected by a 90-day cooldown after completing a donation to safeguard health.
  • Impact History: Track personal donation certificate records and total lives impacted.
🏥

As a Patient / Requester

  • Create Urgent Requests: Specify patient name, blood group, component (whole blood, platelets, plasma), units needed, hospital, and deadline.
  • Real-time Donor Responses: Receive incoming offers from registered donors.
  • Accept / Decline Donors: When an offer is accepted, mutual phone and contact details unlock for hospital coordination.
  • Confirm Transfusion: Once blood is received at the hospital, confirm the donation to formally record it.
  • Report Abusive Content: Flag suspicious or duplicate requests with automatic anti-spam rate limiting.
🤝

Community & Friends

  • Build Trusted Circles: Connect with friends and relatives via friend requests.
  • Instant Emergency Reach: Quickly view friends list with their blood group, phone number, and last donation date.
  • Search & Filter: Instantly filter friends by blood group in an emergency to know who to call first.
🛡️

As an Administrator (Trust & Safety)

  • Review Reports: Inspect reported users and flagged requests with reporter statements.
  • Execute Sanctions: One-click action to block fraudulent users or cancel illegitimate requests.
  • Append-Only Audit Logs: Every admin action (role changes, bans, cancellations) is immutably recorded with changeset metadata.
  • User Management: Elevate staff to Admin or demote/block accounts.
  • System KPIs: Real-time statistics on open vs fulfilled requests, active donors, and pending safety flags.
  • Cache Control: Support for instant direct-to-database fresh reloads bypassing Redis.

⚡ Complete Feature Execution Flows

Tracing how user actions travel through client components, API routes, controller methods, service functions, and database updates.

Flow 1: Blood Request Lifecycle (Creation ➔ Matching ➔ Transfusion Confirmation)

A

1. Requester Submits Request

Page /requests/new gathers patient information, blood group, units, hospital address, and map coordinates.

POST /v1/requests ➔ RequestsController.create() ➔ RequestsService.create()
B

2. Geo Point & PostGIS Persistence

Backend parses latitude/longitude into a PostGIS point ST_SetSRID(ST_MakePoint(lng, lat), 4326) and saves the BloodRequest entity with status OPEN.

requestRepository.save(entity) ➔ triggers PushSubscriptionsService.sendToNearbyDonors()
C

3. Donor Smart Feed Matching

Eligible donors open /browse. SmartFeedService evaluates blood compatibility matrix and calculates distance in KM using ST_DistanceSphere.

GET /v1/smart-feed ➔ SmartFeedController.getFeed() ➔ SmartFeedService.getFeed()
D

4. Donor Offers to Help

Donor views request at /requests/[id] and clicks "Offer to Help".

POST /v1/responses ➔ ResponsesController.create() ➔ ResponsesService.create()
E

5. Requester Accepts Donor

Requester reviews applicant profile and clicks "Accept". Contact numbers are revealed to both parties.

PATCH /v1/responses/:id/status ➔ ResponsesService.updateStatus(ACCEPTED)
F

6. Donation Confirmed & 90-Day Cooldown Applied

At /history, confirmation button is clicked. Creates Donation record, marks request as FULFILLED, sets donor's last_donation_date = NOW() and is_available = false.

PATCH /v1/donations/:id/confirm ➔ DonationsService.confirm()

Flow 2: Reporting, Moderation & Append-Only Audit Logging

1

User Files Safety Report

User clicks Report on a suspicious request. Frontend submits target type and reason. Redis enforces 15-min duplicate report cooldown.

POST /v1/reports ➔ ReportsService.create()
2

Admin Moderates in Admin Portal

Admin opens /admin/reports, reviews evidence, selects "ACTIONED", and chooses "Block User" or "Cancel Request".

PATCH /v1/reports/:id ➔ ReportsService.update()
3

Immutability & Cache Invalidation

Action records an immutable record in audit_logs table. Reports and Dashboard stats caches in Redis are cleared.

AuditLogsService.record() ➔ Invalidate Redis keys: 'reports:*', 'audit_logs:stats'
